## 0. 摘要

我们在 41 个车载域工具、7993 条清洗后的中文指令上，比较两种把工具定义交给模型的方式：
**放在上下文里**（P1，标准 JSON schema，约 5563 tok/请求）与**训进权重里**（P2，输入只有 84 tok 的格式说明）。
两者输出格式、金标、解析器、评测脚本完全相同。

**结论三条。**

1. **可行性成立，且质量打平。** 无 schema 的 LoRA SFT 把工具调用从 0% 提到 **81.76%（4B）/ 75.73%（0.6B）**；
   作为对照，用同样数据但把 schema 留在 prompt 里训练，在 schema 在场的评测上得到 **77.59%**。
   **两条路统计等价**（同为 0.6B LoRA）：75.73%（训 P2）vs 77.59%（训 P1），
   配对差 −1.85 pt（95% CI ±2.46，McNemar p=0.175），且方向在 dev 上相反（附录 D）。
2. **知识进不进权重，取决于训练时它在不在上下文里。** 迁移是单向的：无 schema 训练 → 有 schema 评测 48.22%（能迁移）；
   有 schema 训练 → 无 schema 评测 **0.00%**（完全不迁移）。后者不是格式崩（格式合法率 97.8%），
   是**词表崩**（工具名退回 `播放歌` / `get_temperature`，Tool Acc 13.3%）。
3. **收益在成本，不在质量。** 推理省 5563 tok/请求；训练每 epoch 便宜约 45 倍（110 tok/条 vs 5673 tok/条）。
   实测（4B，固定输出 32 token）：冷启 TTFT 359.6 → 13.3 ms（27×）；
   开前缀缓存后单用户延迟只差 1.10×，但**100 并发下输出吞吐差 4.43×**（不开缓存 47×），
   **KV 占用差 67×**——缓存补回 prefill，补不回 decode 时的注意力与显存。
   训练只用了 **0.8% 的可训练参数**（4B LoRA, 33 M）和单卡 **18 分钟**（3 epoch）。

**边界**：41 个封闭工具集，单轮，中文；75.73%/81.76% 是封闭集上的读数，不外推到开放工具集。
延迟在单卡 4090 上离线实测，倍率可参考、绝对值不可外推。

## 1. 问题

### 1.1 主问题

**能否把工具训进模型权重，从而在上下文中不提供任何 tool schema 的情况下，模型依然能正确完成工具调用？**

### 1.2 子问题

1. **可行性**：拿掉工具清单之后，模型能不能凭参数化记忆完成工具调用？训练数据的上下文里完全没有工具定义，输出仍是模型原生的 tool call 格式。
2. **收益**：牺牲了通用性和灵活性之后，换来的到底是什么？
   - 是更短的 TTFT？——**SIP 的 schema 是逐字节固定的前缀**，前缀缓存（vLLM APC / SGLang RadixAttention）
     能补回 prefill，但补不回 decode 时的 KV 读取。实测结果见 §5.2b。
   - 还是上下文预算？——前缀缓存省的是算力，不是窗口。schema 占的 token 是永久占用。
3. **代价**：标准 tool call 能力掉了多少（灾难性遗忘）？长尾工具上会不会崩？多轮下参数化记忆衰减多快？
4. **归因**：把清单挪出上下文带来的收益，多少来自「训练」、多少来自「清单位置」？
   只有补上「用 P1 训练」的对照臂，前三个问题才能回答。

### 1.3 本文档不回答

- **紧凑输出格式（function token）**：见 §5.3 说明为什么本实验不做。
- **多 tool call（一次输出多个）**：本版不做，但已确认为可行的后续方向。详见 **附录 C — T1**。
- 拒答 / 无关工具识别
- 生产级 serving 优化
- 超过 41 个工具的规模外推（只在讨论里提及）

## 2. 实验设计

### 2.1 两种工具调用范式

单一自变量：**输入里有没有工具清单**。输出格式两边完全一致，都是 Qwen3 原生的标准 tool call。

| | 工具清单 | 格式说明 | 输出 |
|---|---|---|---|
| **P1** | 完整 JSON schema | 有 | `<tool_call>{"name":..., "arguments":{...}}</tool_call>` |
| **P2** | **无** | 有 | 同上 |

**P1 → P2 的唯一差别就是删掉 `<tools>...</tools>` 整块**，其余一字不改。金标、解析器、评测脚本全部共用。

两者完整的 prompt 见 §2.4.9（用同一个真实样本展开）。

### 2.2 三个模型

| 编号 | 底座 | 训练数据 | 训练方式 |
|---|---|---|---|
| **M1** | Qwen3-0.6B / 4B base | 不训练 | — |
| **M2** | 同上 | **P2**（输入无 schema） | SFT |
| **M2′** | 同上 | **P1**（输入含 schema） | SFT |

M2′ 是**归因用的对照臂**：同样的样本、同样的预算，只把训练输入换成「schema 在 prompt 里」。
没有它，`M2/P2` 与 `M1/P1` 的对比会同时变「训练」和「清单位置」两个因素。

**实际训练配置**（`src/train.py`，详见 DECISIONS D8.1–D8.5、D9.2）：

| 项 | 值 |
|---|---|
| 数据 | `train_P2_d.jsonl` / `train_P1_d.jsonl`，7993 条，**同一批 query** |
| loss | 只算 assistant target（prompt 全 mask 成 −100） |
| max_len | 256（P2，mean 110 tok）/ 6144（P1，mean 5673 tok） |
| batch | 8 × accum 4（P2）；1 × accum 32（P1，长序列） |
| lr | 全参 2e-5；LoRA 1e-4，warmup 3%（按优化器步数） |
| LoRA | r=16, alpha=32, dropout 0.05，全线性层 |
| epoch | 3（固定，dev 上选 epoch，test 只跑最终模型） |
| seed | 42（单 seed；同配置重跑的方差已实测，见 §3.4） |

三臂：**0.6B 全参 / 0.6B LoRA / 4B LoRA**。4B 全参在 24 GB 卡上不可行（估 48–64 GB）。

### 2.3 完整矩阵（3 × 2）

| 训练 \ 评测 | P1（有清单） | P2（无清单） |
|---|---|---|
| **M1** 未训练 | 天花板 | 地板（对照） |
| **M2** 训 P2 | 迁移检查 | **训练目标** |
| **M2′** 训 P1 | **对照目标** | 归因关键格 |

四个关键读数：

- **地板**：`M1/P2 ≈ 0`，否则实验不成立（base 本来就能猜）
- **可行性**：`M1/P2 → M2/P2`（训练前后的同一范式）
- **质量对比**：`M2/P2` vs `M2′/P1` —— 两条对角线的比较，**这才是「参数化 vs 上下文」的干净对比**
- **归因**：`M2′/P2` —— 训练时见过 schema、推理时拿掉，还剩多少？这是「知识是否真的进了权重」的判据

### 2.4 数据

#### 2.4.1 源数据：MAC-SLU

| 项 | 值 |
|---|---|
| 全称 | MAC-SLU（Multi-domain Automotive Cockpit Spoken Language Understanding） |
| 来源 | HuggingFace `Gatsby1984/MAC_SLU` |
| 许可 | Apache-2.0 |
| 语言 | 中文，真实车载口语指令 |
| 规模 | train 18000 / dev 1391 / test 1151 |
| 字段 | `id`, `query`, `semantics`, `split_sens` |

一条原始记录长这样（train id 1153）：

```json
{
  "query": "关闭左前阅读灯",
  "semantics": {
    "意图1": {
      "车载控制": [
        {"name": "intent",   "value": "车身控制"},
        {"name": "操作",      "value": "关闭"},
        {"name": "位置",      "value": "左前"},
        {"name": "对象",      "value": "阅读灯"},
        {"name": "车内灯类型", "value": "阅读灯"}
      ]
    }
  },
  "split_sens": ["关闭左前阅读灯"],
  "id": "1153"
}
```

**结构解读**：

- `semantics` 是 `{意图N: {域: [槽位, ...]}}`。`意图N` 是第 N 个意图（多意图时会有 `意图1`、`意图2`…），**不是** `意图1` 就代表单意图——它只是编号。
- `域` 是 8 个之一：`车载控制`(9747) / `音乐`(2833) / `地图`(1825) / `影视`(737) / `天气`(418) / `打电话`(257) / `收音机`(115) / `播放控制`(77)。
- `槽位` 是扁平的 `{"name": ..., "value": ...}` 对，**无序、无类型、无嵌套**。意图本身也是槽位（`name == "intent"`）。
- `split_sens` 是把 query 按语义切片的列表（「打开主驾驶座椅按摩**并且**调节到腰部」→ 2 片），标注质量参考用。

各 split 的标注完整度：

| split | 条数 | 有意图标注 | 多意图 | 意图数分布 |
|---|---|---|---|---|
| train | 18000 | 12694 (70.5%) | 2676 (14.9%) | {0: 5306, 1: 10018, 2: 2183, 3: 379, 4: 85, 5: 27, 6: 1, 7: 1} |
| dev | 1391 | 972 (69.9%) | 204 (14.7%) | {0: 419, 1: 768, 2: 166, 3: 26, 4: 10, 5: 2} |
| test | 1151 | 1125 (97.7%) | 299 (26.0%) | {0: 26, 1: 826, 2: 246, 3: 50, 4: 2, 5: 1} |

**注意 test 的分布和 train/dev 明显不同**（97.7% vs 70.5% 有标注，26.0% vs 14.9% 多意图）。这不是同一个采集批次。评测时 dev 与 test 合并前需注意这一点。

#### 2.4.2 原始标注不能直接当 tool call 用：三个结构问题

**(1) `车身控制` 是巨型桶。** 它是 `车载控制` 域下的一个意图值，占了 7189 条（全 train 的 40%）。它把空调、座椅、车窗、天窗、氛围灯、后视镜……全塞进同一个 intent，真正的区分信息在 `对象` 槽里。而 `对象` 有 **332 种取值**，其中 **1178 条（16.4%）缺 `对象`**。

`对象` 取值 top 20：

| 对象 | 条数 | 对象 | 条数 |
|---|---|---|---|
| 空调 | 1707 | 后视镜 | 100 |
| （缺失） | 1178 | 方向盘 | 67 |
| 座椅 | 1176 | 大灯 | 62 |
| 车窗 | 747 | 扶手 | 57 |
| 天窗 | 221 | 香氛 | 52 |
| 遮阳帘 | 155 | 后备箱 | 52 |
| 氛围灯 | 130 | 扶手台 | 49 |
| 窗户 | 122 | 天幕 | 48 |

如果直接把 `车身控制` 当工具，这个工具会占 40% 训练数据、且金标不唯一（「开空调」和「开座椅」会是同一个 tool call）。**必须按 `对象` 拆。**

**(2) 槽位组合极不规整。** 同属一个工具的样本，槽位签名几乎条条不同（详见 §2.4.6）。

**(3) 参数里有大量自由文本。** 歌曲名、歌手名、片名、联系人、POI 名称……这些是开放词表，无法枚举成 `enum`，只能作为自由字符串生成。这决定了 schema 该怎么写（详见 §2.4.5）。

#### 2.4.3 数据清洗流程

**总览**

```
MAC-SLU 原始 JSONL
  │
  ├─ S1    工具面拆分      车身控制+对象 → veh.<对象>；其余意图 → it.<意图>
  ├─ S2    样本级过滤      丢：无意图 / 多意图 / 缺对象 / 工具 <30 条
  ├─ S3    槽位名归一化    丢噪声槽位；合并同义槽位名（判据：取值域包含度）
  ├─ S4    槽位值归一化    (工具,槽位) 对逐对聚类 → 映射表（S4.1–S4.5）
  ├─ S4.6  enum 长尾过滤   enum 只列 train 中出现 ≥2 的值（**不丢样本**）
  ├─ S4.7  剔除空工具      该工具在 eval 侧无任何样本 → 剔除
  ├─ S5    金标构造        (工具, 参数 dict)，缺省参数省略
  ├─ S5.2  参数契约        每工具 1–4 个参数；砍掉长尾参数，必填缺失则补或丢样本
  ├─ S5.1  描述生成        工具/参数 description（**只读 train 语料**）
  └─ S6    分层标记        eval 样本打 seen / unseen
```

产物：`out/cleaned/{train,dev,test}.jsonl` · `out/schema/tools.json` · `out/manifest.json`（含 sha256）

**可复现性**：`rules/` + `src/clean/` + 原始数据，跑 `python3 -I src/clean/build.py` 得到**逐字节相同**的产物（已连续两次运行验证 sha256 一致）。

**贯穿全流程的一条原则：**

> **LLM 只做「提议」，人做「决定」，脚本做「执行」。**
> 被 review 的产物是**表**（`rules/*.tsv`），不是代码。表可 diff、可版本控制、可附进报告；执行脚本固定，不需要 review。

这条原则同时管住三件事：成本（查表 O(1)，不逐行调 LLM）、可复现（表不变则结果不变）、可审计（读者能逐条对回原始数据）。

**留痕**：每一步的输入文件、输出文件、样本计数、丢弃原因分解，全部写入 `out/manifest.json`（含 sha256）；所有规则以 TSV 存在 `rules/` 下；决策理由记在 `DECISIONS.md`。

##### S2 样本级过滤

```
train 18000
 ├─ 无意图标注      5306  29.5%   ← 丢弃
 ├─ 多意图          2676  14.9%   ← 丢弃
 ├─ 车身控制缺对象     821   4.6%   ← 丢弃
 ├─ 过筛            9197  51.1%
 ├─ 工具 <30 条      978   5.4%   ← 丢弃（279 个工具）
 ├─ 最终训练集       8219  45.7%   （41 个工具）
 └─ S5.2 参数契约     7993  44.4%   （裁参数 + 补全 + 丢 2.7% 缺参样本）
```

**评测集**：dev + test 同口径清洗后 = **1235 条**（588 + 647），覆盖全部 41 个工具。
（S5.2 之前是 1272 条。）

**为什么无意图标注的 29.5% 必须丢弃，而不是当负样本**：这里面混着大量**漏标**。例如：

```
{"query": "HUD调到最低",    "semantics": {}, ...}   ← 明显该是 veh.HUD
{"query": "帮我播一些相声",   "semantics": {}, ...}   ← 明显该是 it.播放音乐
{"query": "退出PM2.5设置项", "semantics": {}, ...}   ← 可能是 it.车机控制
```

当负样本会教模型「这些 query 不该调工具」，直接污染工具选择的决策边界。

**两条实测结论**（决定了后面不需要处理的情况）：

- **样本内重复槽位名：0%** —— 每个槽位名在一条样本里最多出现一次，不存在多值参数
- **重复 query：0** —— 18000 条全唯一，没有去重问题

##### S3 槽位名归一化

###### S3.1 丢弃噪声槽位

| 槽位 | 出现 | 丢弃理由 |
|---|---:|---|
| `intent` | 16009 | 已用于工具面拆分 |
| `对象` | 9268 | 已进工具名 |
| `操作_concrete` | 1798 | 取值只有 到/为/至/true/成，无语义 |
| `sys.*` | 54 | 指代(38) / 序列号(14) / 页码(2)，系统标注 |
| `action` `object` `feature` `body` `part` | 各 1 | 只有 1 条样本，明显误标 |
| `车内灯类型` / `车外灯类型` | 218 / 212 | 取值是 `对象` 的子集，冗余 |
| 出现 < 20 次的槽位名 | 68 | 长尾噪声（脚本按 `min_slot_count=20` 过滤） |

###### S3.2 合并同义槽位名

**判据不是「名字像不像」，是取值域包含度**：`|A∩B| / min(|A|, |B|)`。

| 包含度 | A | B | \|A\| | \|B\| | 判定 |
|---:|---|---|---:|---:|---|
| **1.00** | 位置 | 车载交互位置 | 183 | 9 | **同义，合并** |
| 0.47 | 功能 | 子功能 | 246 | 112 | 部分重叠，**不合并** |
| 0.50 | value | 方向偏移量 | 901 | 14 | 部分重叠，**不合并** |

**反例——名字像但取值域完全不重叠，绝不能合并**：

| A | B | A 的取值 | B 的取值 |
|---|---|---|---|
| 位置 | **身体位置** | 副驾 / 主驾 / 前排 / 后排 | 脚部 / 腰部 / 头部 / 肩部 |
| 操作 | **`__act__`** | 打开 / 关闭 / 调节 / 播放 | request / confirm / querymore（**对话行为**） |
| 对象功能 | **功能** | 通风 / 按摩 / 加热 / 蓝牙 | 驻车 / 智慧巡航 / 车道辅助（**ADAS**） |
| 调节内容 | **`__tgt__`** | 模式 / 温度 / 方向 / 风量 | 天气 / 气象 / 路况 / 剩余时间 |

**结论：槽位名层面只需 1 处合并**（`车载交互位置 → 位置`），其余保持原样。这一步很轻。

##### S4 槽位值归一化（主要工作量）

###### S4.1 先分类：哪些槽位需要建表

按「取值种数 / 出现次数」比值分三类。实测（脚本 `src/clean/dump_candidates.py`，输出 `out/audit/s3_slot_counts.tsv`）：

| 类型 | 判据 | 槽位数 | 样本数 | 处理 |
|---|---|---:|---:|---|
| **枚举** | 比值 ≤ 0.1 | **6** | 11964 | 建表，映射到规范形，schema 列 `enum` |
| **半开放** | 0.1 < 比值 ≤ 0.5 | **31** | 5413 | 建表，但 schema 只声明 `string` |
| **自由文本** | 比值 > 0.5 | **24** | 4311 | **不建表**，schema 声明 `string` |
| （丢弃） | 出现 < 20 次 | 68 | 486 | S3.1 已丢弃 |

**枚举 6 个**：`操作` / `调节内容` / `__act__` / `__tgt__` / `排行榜` / `来源`

**自由文本 24 个（一行表都不用写）**：`歌曲名` / `poi类型` / `片名` / `歌手名` / `终点名称` / `联系人` / `poi名称` / `主题` / `途经点名称` / `路线偏好` / `poi修饰` / `功能` / `号码` / `事件` / `黄页号码` / `专辑名` / `上映时间` / `终点类型` / `区域` / `子功能` / `地图尺寸` / `摄像头模式` / `电影人` / `集数`

###### S4.2 建表流程

```
① 枚举       对每个 (工具, 槽位) 对，列出全部取值 + 频次     ← 脚本产出，纯统计
② LLM 聚类   只喂「取值 + 频次」，给出合并建议              ← ✗ 不喂 query、不喂答案
③ 人工 review 确认 / 修改 → 定表
④ 固定脚本读表执行
```

**为什么只喂词表不喂 query**：一旦 LLM 看到 query，它就可能做「这两条 query 语义相同所以合并」的判断——那才携带了 query→answer 的信息。只喂词表，表就是**标注词表的函数**，跟数据划分无关。

###### S4.3 规范形用中文，且不做轴拆分

**规范形取簇内最高频的原形**：

```
主驾 / 主驾驶 / 主驾的 / 主驾座 / 驾驶位 / 驾驶座  →  主驾
调节 / 调 / 调到 / 调整 / 调一点 / 调为 / 调整为   →  调节
打开 / 开启 / 开 / 开开 / 开一下 / 开下            →  打开
```

**判据是「金标唯一」，不是「语义正确」**：

| | 判据 | 处理 |
|---|---|---|
| **必须合并** | 不合并则同一 query 有多个合法答案 | 主驾 / 主驾驶 → 主驾 |
| **不合并** | 只是 enum 多几个值 | `左前` 保留为 `左前`，不并进 `主驾`，也不拆成 `side=左, row=一排` |

**不做轴拆分**的理由：本实验不是在做通用车型 schema。P1 和 P2 看到的是**同一个 enum**，多几个值不偏袒任何一臂。

**硬约束只有两条**：映射必须是**函数**（一值一映射），规范形集合必须**可枚举**。

###### S4.4 建表数据范围：全量

**用全量数据建表，不用 train-only。** 三条理由：

1. **映射表定义的是输出空间**（工具的参数取值域），生产环境里是**给定的**，不是模型学出来的。用全量建表是定义任务，不是拟合测试集。
2. **P2 的知识只来自 train，跟表建在哪无关。** 表建在全量上，P2 依然会在 train 没见过的规范值上失败——失败模式不会消失，只是从「样本被丢弃」变成「样本被答错」。
3. **「答错」比「丢弃」有信息量。** train-only 会直接丢掉 21.9% 的 eval 样本（见 S6）。

###### S4.6 enum 长尾过滤（只清 enum，不丢样本）

**问题**：enum 槽位里混着标注噪声。实测 `座椅` 的 `操作` 候选值里出现过 `可以关了`、`弄回去`、`座`、`抬` 这类值——它们对 P1/P2 都是纯噪声，且会把 schema 撑爆。

**决策**：取值种数 ≤ 30 的槽位，enum 只列 train 中出现 **≥2 次**的规范值。**稀有值本身仍是合法金标，只是不进 enum。**

**为什么只清 enum、不丢样本**：这直接对应 §2.4.3 S4.4 的「全量建表 + seen/unseen 标记」原则——用更稀有值的样本会被 S6 **自然标成 `unseen`**，在报告里分层呈现，而不是被悄悄删掉。

> 第一版做的是「丢样本」，结果 train 8219 → 3586（丢 56%）、工具从 41 掉到 27。
> 那个做法与「不丢样本、分层报告」的原则自相矛盾，已废弃。**这个取舍记在 `DECISIONS.md` 里供复查。**

**只对 enum 槽位生效**：半开放槽位（`value` 529 个取值、`模式` 225 个）本来就声明为 `string`、不列 enum，不要求唯一，不该过滤。

###### S4.7 剔除空工具

**另有一条工具级剔除**：某工具在 eval 侧（dev+test）一条样本都没有 → 剔除该工具。
这类工具在评测里无法产生任何读数，留着只会污染工具计数。实测剔除 **0 个**（S2 的阈值已经把它们筛掉了）。

##### S5 金标构造

```json
{"tool": "座椅",
 "arguments": {"对象功能": "按摩", "操作": "切换", "调节内容": "模式"}}
```

- 参数名用归一化后的槽位名（中文），参数值用规范形（中文）
- **缺省参数直接省略**（不写 `null`）——样本内重复槽位名 0%，不存在多值参数
- 参数顺序**无所谓**（P1/P2 都是具名参数，解析器解成 dict）

~~**每个工具的 schema** = 该工具下出现比例 ≥2% 且绝对次数 ≥5 的槽位名集合。归一化后中位数 5 个参数（`veh.座椅` 原始 12 个槽位名 → 9 个参数）。~~

> **已废弃**。这条阈值口径把「该工具**可能**出现的参数并集」当成了 schema，而金标是「这条 query **实际**标注的参数」。
> 两者口径不一致，模型照 schema 补全反而被判错。取而代之的是 **S5.2 参数契约**（见下）。
> 这段仍保留在此，是因为它对旧口径的历史读数仍然成立。

##### S5.1 描述生成

工具的 `description` 和每个参数的 `description` 是 schema 的一部分——**P1 在 prompt 里能看到，P2 看不到**，所以它是 P1/P2 差异的一个组成部分，必须显式构造，不能留空。

**产物同样是一张表**：`rules/descriptions.tsv`，格式 `tool / slot / description`：

```
slot = *        → 该工具的描述
tool = *        → 该槽位的全局默认描述
(tool, slot)    → 该工具下的覆盖（优先级最高）
```

解析优先级：`(tool, slot)` > `(*, slot)` > 槽位名兜底。

**写法约定**：描述说清「这个参数是什么」，**不重复枚举取值**（`enum` 字段已经承载取值）。

**证据来源分两类**（`src/clean/dump_descriptions.py` 导出，`out/audit/desc_{tools,slots}.tsv`）：

| 证据 | 来源 | 说明 |
|---|---|---|
| 槽位名、取值、频次 | 全量 | 无争议 |
| 示例 query | **只用 train split** | 见下 |

**为什么示例 query 只用 train**：`description` 属于 schema，是 P1 在推理时**给定的任务定义**。用 train 语料写描述，等同于在训练集上做 prompt engineering，是标准做法；**用 eval 语料写则会携带评测集信息，构成泄漏**。这与 S4.4「建表只喂词表、不喂 query」是同一条原则的延伸。

**实测**：41/41 工具、94/94 参数全覆盖（`out/manifest.json` 与 `build.py` 的 S5.1 覆盖检查）。

**代价**：description 自身约占 **1560 tok**，是 schema 块的 **27.4%**。

| | tokens |
|---|---:|
| P1 的 `<tools>` 块（含 description） | **5563** |
| 同上去掉 description（按 schema 文本量估算） | 4003 |
| description 净开销 | **1560**（+39%） |

> 旧的 S5 口径（216 个参数）下这三行分别是 7172 / 4916 / 2256（+45.9%）；
> S5.2 契约把参数压到 94 个之后绝对值变小，但 description 的相对占比仍接近三成。
>
> 这顺带给出一个**免费的消融臂**：把 description 全部删掉，schema 立刻省 27%。
> 如果「P2（无 schema）≈ P1（schema 去掉描述）」，那说明模型并不需要这些描述——那本身就是个结论。
> **本实验暂不做这一臂，但记录在此。**

##### S5.2 参数契约（schema 与金标对齐）

**问题**：S5 原来的口径下，schema 收的是「该工具**可能**出现的参数并集」（≥2% 且 ≥5 次），
金标收的是「这条 query **实际**标注的参数」。两者不是一回事，于是模型照 schema 把参数补全，
反而被判错。最极端的例子：

```
schema（旧）  播放收藏：操作 / 来源 / 排行榜 / 歌曲名 / 歌手名      ← 5 个参数
金标          {"操作": "播放"}                                   ← 47/119 条只有这一个
```

这不是模型能力问题，是**评测口径问题**。量化后的形状：

| 观测 | 数值 |
|---|---:|
| schema 参数在样本中的**中位覆盖率** | **7%** |
| 金标参数不在 schema 里的样本 | 687（7.2%） |
| 旧 schema 参数总数 | 216 |

**规则**：改用一张人工 review 过的表 `rules/tool_params.tsv` 作为**参数契约**，每行一个 `(tool, slot)`：

| 列 | 含义 |
|---|---|
| `role = required` | 每条样本都必须有这个参数；金标缺失时补 `fill`，补不了就**丢掉该样本** |
| `role = optional` | 金标有就评，没有不评 |
| **不在表里** | **cut**：从 schema 和金标里同时删掉 |

判定方法（全部在 train 上统计，不看 eval）：

- `required`：覆盖率 ≥95%；或该工具覆盖率最高的参数且 ≥75%
- `optional`：其余覆盖率 ≥30% 的参数，每工具最多 2 个
- `fill`：**只允许由工具名唯一确定的常量** —— 全表只有两处：`播放音乐.操作=播放`、`提供地址.操作=查找`。
  内容型参数（片名、城市、终点名称）**一律不补**，那是编造标注。

**结果**：

| | 旧（S5 阈值） | 新（S5.2 契约） |
|---|---:|---:|
| schema 参数 | 216 | **94**（−56%） |
| 每工具参数 中位 / 最大 | 5 / 12 | **2 / 4** |
| required / optional | — | 44 / 50 |
| 金标平均参数数 | 2.38 | **1.73** |
| dev + test 样本 | 1272 | **1235** |
| P1 schema 块 | 7133 tok | **5563 tok**（−22%） |

契约裁剪掉了 **5263 个参数实例**（train 19169 → 13906），补全 **215 条**，丢弃 **263 条样本**
（train 226 / dev 21 / test 16；train 侧占 2.7%）。
丢弃原因全部集中在「必填参数缺失且无法安全补全」，逐槽位计数写在 `out/manifest.json` 的
`s52_drop_reasons` 里。

**为什么这比「提高模型能力」更根本**：本实验问的是「一个**相对简单**的工具能不能被后训练训进权重」。
旧口径把每个工具都变成了「5–12 个可选参数、金标只标其中 1–2 个」的开放任务，
测的是参数猜测能力，不是工具记忆能力。契约把任务压回「选对工具 + 填对 1–2 个必填参数」，
这才是 P1/P2 差异应该被测量的地方。

**已知边界（记录，不修）**：

- `查询路况`、`查询路程` 两个工具在契约里没有留下任何参数（历史标注过于稀疏），
  schema 里是空 `arguments`。它们在 eval 里共 **12 条**（1.0%），这 12 条的 Call Acc 退化成 Tool Acc。
- 被 cut 的参数**不再被评测**：模型写对也不加分，写错也不扣分（宽松口径本身也忽略多余参数）。
  这是有意的——本实验不测复杂参数填充。

##### 附：标注规整度实测（本实验不需要解决，但记录在此）

位置参数格式（`<|tool_N|>(a, b, c)`）要求每个工具有唯一确定的参数顺序。原始标注没有这个性质。实测三种签名口径下的一致性：

| 签名口径 | 一致样本 / 总数 | 一致率 |
|---|---|---|
| 有序 (槽位名, 值) | 340 / 8219 | **4.1%** |
| 有序 (槽位名) | 3050 / 8219 | 37.1% |
| 无序 (槽位名) | 3602 / 8219 | 43.8% |
| 无序 (槽位名)，前 20 工具 | 3130 / 7369 | 42.5% |

**三个数字含义完全不同，引用时必须说清口径**：

- **4.1%（含值）** 才是真实情况——同属 `it.播放音乐` 的 2317 条样本里有 1929 种不同的 (槽位名, 值) 组合。这是自由文本参数造成的。
- **43.8%（无序名）** 是「参数集合是否稳定」，才是判断「能不能定义 schema」的口径。
- 两者差距说明：**参数名相对稳定，参数值几乎全不同。**

**本实验不受此影响**：P1/P2 都用**具名参数**，顺序无关，解析器解成 dict 后键序不影响判定。

**但如果将来要做紧凑的位置参数格式，这就是硬阻塞**——必须先为 41 个工具各定一个 canonical 参数序（缺省位置填 `null`），否则在构造上就学不会。详见 §5.3。

### 2.5 指标

| 指标 | 定义 |
|---|---|
| **Call Acc（主）** | 工具名对，且**金标里的每个参数都正确出现**（`gold ⊆ pred`）。模型多写的参数不扣分 |
| **Call Acc（严）** | 工具名对，且参数集合**完全相等**（`gold == pred`）。次要指标，衡量接口纪律 |
| **Tool Acc** | 只看工具名 |
| **Arg P / R / F1** | 参数级精确率 / 召回率 / F1（区分「选对填错」） |
| **schema 外参数率** | 预测里出现 schema 未声明参数的比例（接口纪律的另一个读数） |
| **格式合法率** | 输出能被解析器解析的比例（单列，不计入 Acc 分母） |
| **Prompt tokens** | 输入长度 |
| **Output tokens** | 输出长度（= decode 步数） |
| **TTFT（冷启）** | 无前缀缓存，`max_tokens=1` 的端到端耗时（prefill + 1 步 decode） |
| **TTFT（APC）** | 开启前缀缓存 |
| **req/s** | 单位时间完成的请求数；**只有固定输出长度时才可比** |
| **输出 tok/s** | 单位时间生成的 token 数；吞吐的公平口径 |
| **输入 tok/s** | 单位时间处理的输入 token；开 APC 时是含缓存命中的上界 |
| **峰值显存** | — |

**为什么主指标用宽松口径**：金标是「query 里**显式提到**的参数」的稀疏标注，不是「工具接口的完整调用」。
模型多写一个 schema 内、但金标没标的参数（例如补上 `操作=播放`），在真实系统里是合理行为，
不应判错。同理，模型写出 schema 外的参数按宽松口径也不扣分，但单独报「schema 外参数率」记录接口纪律。

严格的集合相等等价于「模型必须猜到标注员的省略习惯」，这正是 S5.2 之前的评测把 P1 压到 17% 的原因之一。
两个口径**同时报**，读者可以各取所需。

**运行噪声（实测）**：`do_sample=False` **不等于**可复现。vLLM 的 paged-attention 与 batch 调度
会在 bf16 下产生数值上不同的 logits，greedy argmax 在接近平局时翻转。同一配置连跑两次，
dev 上有 **4.6%（27/588）** 的样本输出不同，指标跨度 **±0.5 pt** 左右。
所以：不写「greedy ⇒ 确定」，跨配置比较时**差异小于 1 pt 一律不解释**。详见 §3.4。

**吞吐测量必须固定两件事**：输出长度（`ignore_eos=True` + 固定 `max_tokens`）与并发数。
否则 req/s 会把「请求更便宜」误记成「引擎更快」，见 §5.2b。

**推理设置必须固定**：`do_sample=False`（greedy）、`enable_thinking=False`。

Qwen3 的 `generation_config.json` 默认是 `do_sample=true, temperature=0.6, top_k=20, top_p=0.95`，且 chat template 默认开 thinking——不显式关掉，3 个 seed 的差异会被采样噪声污染，而且 0.6B 会在 `<think>` 里烧掉大量 token 且极不稳定。

### 2.6 事先定下的判定门槛

| 判定 | 条件 | 不满足时的解释 |
|---|---|---|
| **地板成立** | `M1/P2 ≤ 0.05` | base 模型本来就能猜 → P1 天花板不可信，实验不成立 |
| **可行性成立** | `M2/P2 ≥ 0.90 × M1/P1` | 「训进去了」不成立 |
| **遗忘可接受** | `M2/P1 ≥ 0.95 × M1/P1` | 代价过大 |
| **长尾不崩** | `<60` 箱内 `M2/P2 ≥ 0.75 × M1/P1` | 纯记忆对长尾不成立 |

### 表 2b — 控制实验：训练用 P1 还是 P2（0.6B LoRA，test）

| 训练数据 | 评 P1（清单在 prompt） | 评 P2（无清单） |
|---|---:|---:|
| —（M1 未训练） | 26.74% | 0.00% |
| **P1**（M2′） | **77.59%** | 0.00% |
| **P2**（M2） | 48.22% | **75.73%** |

**对角两格：75.73% vs 77.59%，差 −1.85 pt（95% CI ±2.46，McNemar p = 0.175）。**

两个结论：

1. **质量统计等价**。上下文方案在 test 上高 1.9 pt，但在 dev 上低 2.0 pt（附录 D）——**方向会翻**，
   且两者都小于置信区间。配对比较：647 条里两边都对 463 条，只有 M2 对 27 条、只有 M2′ 对 39 条，
   两边都错 118 条。差异不显著，只能判「等价」。
2. **迁移不对称**。无清单训练 → 有清单评测得 **48.22%**（能迁移）；
   有清单训练 → 无清单评测 **0.00%**（完全不迁移）。
   拿掉清单就归零，且不是格式崩（格式 97.8% 合法），是**词表崩**（Tool Acc 13.29%，工具名退回
   `播放歌` / `get_temperature`）——清单在上下文里时，模型学到的是「照抄」，不是「记住」。

> 所以「M2/P2 比 M1/P1 高 35 pt」**不能**当成参数化的优势：那 35 pt 混淆了「训练」和「清单位置」。
> 参数的真正收益在成本：推理省 5563 tok/请求，训练每 epoch 便宜约 45 倍。

### 3.4 跑间方差：什么量级的差不可解释

- **推理侧**：同一模型、同一输入连跑两次，dev 上有 4.6% 的输出不同，指标差 **±0.5 pt**（§2.5 末）。
- **训练侧**：M2′ 0.6B LoRA 的同一配置跑了两次（都是 1 epoch），dev Call Acc **69.56%** 与 **71.77%**，
  差 **2.2 pt**。两次之间没有任何超参差异。

→ 表 2b 里 1.9 pt 的差**落在噪声内**。这也是本文不把「谁更好」当结论的原因。

## 5. 讨论

### 5.1 三条结论

**1. 可行：无 schema 的工具调用可以被训出来，而且不掉质量。**

4B 在完全没有任何工具定义的输入上达到 **81.76%** Call Acc（严格 80.22%），Tool Acc 96.29%，
格式合法率 100%；训练只用了 33 M 可训练参数（0.8%）和单卡 **18 分钟**（3 epoch，4B LoRA）。

同数据、同预算、只把 schema 留在 prompt 里训练的对照臂（M2′，0.6B LoRA）在 **有 schema** 时得到
**77.59%**；与之同规模的 M2/P2 是 **75.73%**。差 1.85 pt（95% CI ±2.46，McNemar p=0.175），
且 dev 上方向相反——**统计等价**。

> **这是本文的核心读数：把工具定义从上下文挪进权重，质量不变（差异不显著）。**

**2. 知识进不进权重，取决于训练时它在不在上下文里。**

| | 训 P2 | 训 P1 |
|---|---:|---:|
| 评 P2（无清单） | **75.73%** | **0.00%** |
| 评 P1（有清单） | 48.22% | **77.59%** |

（0.6B LoRA，test n=647）

迁移是**单向**的。在 schema 在场的条件下训练，模型学到的是「把输入里的清单抄到输出」；
一旦抽掉清单，它退回 base 的通用词表（`播放歌`、`get_temperature`），Tool Acc 降到 13.3%，
但**格式仍然合法**（97.8%）——所以这不是「忘了怎么调工具」，是「从来没记住接口」。

这条对实践的直接含义：**想让模型记住接口，训练输入里就不能给接口。**
用 function-calling 数据做常规 SFT，学到的是照抄，不是记忆。

**3. 收益在成本，不在准确率。**

| | 上下文（P1） | 参数化（P2） |
|---|---:|---:|
| 推理输入 | 5647 tok | **84 tok**（−98.5%） |
| TTFT 冷启（4B） | 359.6 ms | **13.3 ms**（27×） |
| TTFT + 前缀缓存（4B） | 23.4 ms | **12.1 ms**（1.9×） |
| 单请求生成 32 token + 缓存（c=1） | 379.7 ms | **343.7 ms**（1.10×） |
| 输出吞吐 + 缓存（c=100） | 1300.5 tok/s | **5764.2 tok/s**（4.4×） |
| 输出吞吐 · 无缓存（c=100） | 73.4 tok/s | **3463.4 tok/s**（47×） |
| 每套工具集的 KV 占用（4B） | 0.485 GiB | **0.007 GiB**（67×） |
| 训练每 epoch（0.6B） | 45–60 min | **70 s**（约 45×） |
| 准确率（test） | 77.59% | **75.73%** |

**参数化不是「更准」，是「同样准，但便宜」。** 而且便宜在推理和训练两头，
**前缀缓存只能把推理成本补回一部分**：TTFT 基本补平（1.9×），吞吐和显存补不平（9× / 67×）。

### 5.2 这些结论还没有覆盖什么

- **规模**：41 个工具、7993 条样本、单卡。工具数上百时，训练成本与遗忘曲线都会变。
- **通用性**：没有通用 benchmark 回归测试，不能声称「没有损害」。
- **多轮**：完全未测。
- **延迟的绝对值**：本文在单卡 4090、单请求 / 单批 100 条的离线设置下测（表 4），
  不是生产级 serving 压测；绝对值不可外推到多卡 / 高并发集群，但**倍率关系可参考**。

### 5.2b 前缀缓存能补回多少？——实测

P1 的 schema 块是渲染在 system message 最前面的逐字节固定前缀，正是 APC / RadixAttention
最擅长缓存的东西。所以问题不是「参数化有没有延迟收益」，而是「前缀缓存之后还剩多少」。

**答案是：单用户基本补平，高并发和显存补不平。**

| 4B，前缀缓存开启 | P1 | P2 | 倍率 |
|---|---:|---:|---:|
| TTFT（c=1） | 23.4 ms | 12.1 ms | 1.9× |
| 单请求生成 32 token（c=1） | 379.7 ms | 343.7 ms | **1.10×** |
| 输出吞吐（c=100） | 1300.5 tok/s | 5764.2 tok/s | **4.43×** |
| KV 占用 | 0.485 GiB | 0.007 GiB | 67× |

**为什么并发上去了就补不回来**：前缀缓存省的是 **prefill**。但每生成一个 token，注意力都要把
5647 个 token 的 KV 从显存里读一遍——这笔 **decode 时的带宽开销**不受缓存影响。
并发为 1 时，这点开销被固定成本摊薄，差 1.1×；并发为 100 时，
decode 成为主要工作，差距放大到 4.4×。固定 32 token 时，**每 token 多花约 1.1 ms**。

**所以「schema 在上下文里是免费的，因为可以缓存」这句话是错的。**
准确的说法是：
- **prefill 可以缓存** → 单用户 TTFT 接近免费（仍留 1.9×），单请求延迟差 1.10×
- **decode 的注意力与 KV 占用不能缓存** → 高并发输出吞吐差 4.4×，每套 schema 多占 0.485 GiB
- **不开缓存时** → 吞吐差 47×，且 P1 会饱和在 ~73 tok/s，加并发不再提升

在工具集固定的单租户、低并发场景，参数化的收益主要是上下文窗口和冷启动；
在多工具集 / 高并发 / 每用户定制工具的场景，decode 与 KV 的账才是大头。

### 5.3 为什么本实验没有测试紧凑输出格式

一个自然的追问是：既然要把工具挪出上下文，为什么不顺带把**输出**也压缩成 function token（`<|tool_N|>(a, b)`）？

本实验决定不做，理由是**收益量级不匹配**。实测同一个金标的四种输出写法（金标为中文规范形）：

| 输出格式 | 枚举型 座椅 | 自由文本型 播放音乐 |
|---|---:|---:|
| 完整 JSON `<tool_call>{"name":...}` | 50 | 37 |
| 紧凑具名 `<\|tool_7\|>{位置:副驾,对象功能:按摩,...}` | 34 | 26 |
| 紧凑具名·缩写键 `<\|tool_7\|>{位:副驾,对:按摩,...}` | 32 | 25 |
| 位置参数 `<\|tool_7\|>(副驾, 按摩, ...)` | 31 | 22 |

- 省下来的 token **主要来自丢掉参数名**，而不是丢掉参数名的排列。
- **中文规范形下，位置参数相对紧凑具名只多省 3–4 个 token**——因为中文参数名本身就只有 2–4 个 token（`位置` = 2、`对象功能` = 4、`操作` = 2），跟英文的 `position` / `feature` / `action` 差不多贵。
- 而**位置参数是本实验中唯一需要 canonical 参数序的格式**——即 §2.4.3 附录里那个 43.8% 一致率的问题。紧凑具名则完全不需要。
- 折算到全 eval 集（1272 条，S5.2 前的口径；新口径 1235 条量级不变）：位置参数平均每条省 **14.6** tok，紧凑具名约 **10** tok。对比输入侧的 **5563** tok，是 **1/500** 的量级。

**结论**：紧凑输出格式的收益是每条 10–15 个 decode token（约 0.2–0.4 秒），而它要付出的代价是多一个前置条件（参数序）、多一套解析器、多一次训练。**量级不匹配，故本实验不做。**

如果将来要补，**用紧凑具名而非位置参数**：中文规范形下两者收益几乎相同，而紧凑具名完全绕开参数序阻塞。

### 5.4 与既有工作的关系

华为《From Fixed Keys to Readable Schemas》(arXiv 2609.09476) 报告了「训练时见过的功能上，FT 与 SIP 表现相当（95.5~97.9 vs 97.2~98.7）」。本实验接受这条结论，转而追问它没有回答的部分：**打平之后，把工具挪出上下文换来的到底是什么。**

本实验只覆盖该论文的 **SIP vs「FT-name 变体」**这一段——输入去掉 schema，输出格式不变。论文未写明 FT 的参数格式，本实验在此明确声明：**本实验的输出格式与 SIP 完全一致，差异只在输入侧。**

**与这类工作的差别**：把工具/函数变成可训练的参数，已有若干条路线——把工具名做成特殊 token（ToolkenGPT 一脉）、
在输出侧引入 function token、或直接做 function-calling SFT（Gorilla / ToolLLM 一脉）。
本文不主张「工具可以进权重」这一点是新的；本实验的增量是**控制变量与成本核算**：

1. 同一底座、同一批样本、同一个解析器，只改「schema 在不在输入里」——**训练与推理各改一次，形成 3×2 矩阵**；
2. 由此给出一个干净的反例：**schema 在输入里训练，知识不会进权重**（M2′/P2 = 0.00%）；
3. 同时报质量与成本（token、训练时间），并明确指出延迟一项尚未测。

## 附录 C — 后续工作（未纳入本版）

### T1 多 tool call（**未做**；方向已定）

**结论：可行，且应做；但不纳入本版。** 它不服务于本实验的核心问题（schema 在不在上下文里），而且会给 P1/P2 的对比引入一个无关的失败模式。

**数据实测**（train 多意图 2676 条；每个意图 → 一个 tool call，规范化后样本内去重）：

| | train | dev | test |
|---|---:|---:|---:|
| 原始多意图 | 2676 | 204 | 299 |
| 有 call 的工具不在 41 集合内 → 丢弃 | −783 | −58 | −91 |
| 可用 | 1893 | 146 | 208 |
| 其中样本内重复 call | −88 | −8 | −8 |
| **去重后 ≥2 call** | **1856** | **142** | **203** |
| 去重后降级为 1 call | 37 | 4 | 5 |

**净增：train +1893（+23%），eval +354（+28%）。** 重复标注只有 4.6%，去重即可，不需要额外清洗。

**做法（已定，实施时照此执行）**：

1. `s1_split` 不再丢多意图，每个意图 → 一个 tool call
2. **样本内去重**：规范化后完全相同的 call 只留一个；去重后只剩 1 个 call 的样本降级为单 call 样本，仍可用
3. **任一 call 的工具不在 41 集合内 → 整条丢弃**（932 条）
4. 每个样本带 `n_calls` 字段
5. **评测分层**：主表只看 `n_calls == 1`（与现在的 1235 条完全可比），另加一张 `n_calls >= 2` 的表
6. 多 call 指标 = **集合精确匹配**（所有金标 call 都产出、且无多余 call）+ per-call F1

**为什么分层而不是混进主表**：多 call 引入了一个与 schema **完全无关**的新失败模式——「数不对该输出几个 call」。schema 在不在上下文里，都不告诉模型该输出 2 个还是 1 个。这个失败模式对 P1/P2 是对称的，混进主表只会稀释信号。

**预注册风险**：0.6B 可能根本学不会输出多个 tool call，多 call 表可能全场趋零。**跑之前先确认 `M1/P1` 在多 call 切片上能过某条底线（建议 30% 集合精确匹配）**；过不了就把这一臂降级为「仅记录」，不进主结论。

**后续可选的合成路线**：用单 call 样本合成多 call 数据（把两个独立 query 串起来），作为多 call 数据的补充。**不作为主要目标。**

### D.3 合并后为什么出现两个 78.46%

如果不分 split、把 1235 条合在一起：

| split | 训 P2 → 评 P2 | 训 P1 → 评 P1 | 差 |
|---|---:|---:|---:|
| dev | 81.46%（479/588） | 79.42%（467/588） | +2.04 |
| test | 75.73%（490/647） | 77.59%（502/647） | −1.86 |
| **合并** | **78.46%（969/1235）** | **78.46%（969/1235）** | **0.00** |

479+490 = 467+502 = 969 —— 两个方向相反的差值恰好抵消。**这是数值巧合，不是结构性恒等。**

它说明的是：两个模型的差异（±2 pt）小于两个 split 之间的差异（最大 5.7 pt）。
把 split 混起来报，会让一个偶然的抵消看起来像「精确打平」——这正是本文主表只用 test 的原因之一。

**等价的结构性证据在 test 上同样成立**：647 条里两边都对 463 条，只有 M2 对 27 条、
只有 M2′ 对 39 条，两边都错 118 条；共享错误占全部错误的多数，且集中在近义值未合并
（`降`/`调低`）、大小写（`JANET`/`janet`）、ASR 噪声（`锅风`）这类**数据问题**上。
