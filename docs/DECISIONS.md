# 数据清洗决策日志

> 每个决策的「为什么」。规则本身在 `rules/` 下（可 diff、可 review），
> 执行代码在 `src/clean/` 下（固定不变），复现凭据在 `out/manifest.json`（含 sha256）。
>
> **任何人拿到 `rules/` + `src/clean/` + 原始数据，跑 `python3 -I src/clean/build.py`
> 都能得到逐字节相同的产物**（已验证：连续两次运行 sha256 一致）。

最后更新：2026-10-20

---

## 0. 贯穿全局的原则

> **LLM 只做「提议」，人做「决定」，脚本做「执行」。**
> 被 review 的产物是**表**（`rules/*.tsv`），不是代码。

理由：表可 diff、可版本控制、可附进报告、读者能逐条对回原始数据。代码不行。
成本上查表 O(1)，不需要逐行调 LLM；可复现性上表不变则结果不变。

## S1 工具面拆分

### D1.1 `车身控制` 必须按 `对象` 拆分

**决策**：`车身控制 + 对象 → veh.<对象>`；其余意图 `→ it.<意图名>`（1:1）。

**为什么**：`车身控制` 占 train 的 40%（7189 条），它把空调/座椅/车窗/天窗/氛围灯/后视镜全塞进同一个 intent。
不拆的话「开空调」和「开座椅」会是同一个 tool call，金标根本不唯一。

### D1.2 工具名同义词合并 20 条

**决策**：见 `rules/tool_synonyms.tsv`。窗户/窗→车窗、门→车门、车灯/灯光/车外灯→大灯 等。

**为什么**：不合并则同一物理对象裂成多个工具，每个都拿不到足够训练样本，且工具选择变成纯噪声。

**边界**：只做**同物异名**，不做语义重编码。`天幕` 与 `天窗` 是两个东西，不合并。

### D1.3 工具粒度阈值 = train ≥ 30 条

**决策**：`config.json: min_tool_train_count = 30`。

**为什么**：低于 30 条的工具，模型不可能学会，且 eval 样本也少到不可解读。实测丢弃 279 个工具、978 条样本（5.4%）。

## S2 样本级过滤

### D2.1 无意图标注的 29.5% 丢弃，不当负样本

**决策**：`semantics` 为空的样本直接丢弃。

**为什么**：这里面混着大量**漏标**（`HUD调到最低`、`帮我播一些相声`）。
当负样本会教模型「这些 query 不该调工具」，直接污染工具选择的决策边界。宁可少 29.5% 数据，不要污染的决策边界。

### D2.2 多意图样本丢弃（本版）

**决策**：`len(intents) > 1` 的样本丢弃（train 14.9%）。

**为什么**：本实验的评测是「单次 tool call 的准确率」。支持多 tool call 会把评测复杂度翻倍，
且与 P1/P2 的核心问题（schema 在不在上下文里）无关。**记录为已知的规模限制。**

**⚠️ 该决策已于 2026-10-20 复核，方向改为「后续纳入」**：
多 call 数据实测可行（train 可回收 1893 条 / +23%，eval +354 / +28%，重复标注仅 4.6%）。
做法与分层评测方案已定稿，见 `REPORT.md` **附录 C — T1**。
**本版仍不实施**（不作为主要目标），规则与代码保持现状。

### D2.3 车身控制缺 `对象` 丢弃

**决策**：`对象` 槽缺失的 `车身控制` 样本丢弃（821 条，4.6%）。

**为什么**：拆不出工具名，无法构造金标。

## S3 槽位名归一化

### D3.1 丢弃噪声槽位

**决策**：见 `rules/drop_slots.tsv`，另有两条脚本规则：
- `intent` 槽 → 已在 S1 用掉
- 全量出现 < 20 次的槽位名 → 长尾噪声（68 个）

**为什么**：`操作_concrete`（1798 次）取值只有 到/为/至/true/成 5 种，纯语法噪声；
`action`/`object`/`feature`/`body`/`part` 各只出现 **1 次**，明显误标；
`车内灯类型`/`车外灯类型` 的取值是 `对象` 的子集，冗余。

### D3.2 槽位名合并只做 1 处 —— 判据是「取值域包含度」

**决策**：`车载交互位置 → 位置`（包含度 1.00）。其余不合并。

**为什么**：判据不是「名字像不像」，是 `|A∩B| / min(|A|,|B|)`。实测只有这一对达标。

**四个反例（名字像但取值域完全不重叠，绝不能合并）**：

| A | B | A 的取值 | B 的取值 |
|---|---|---|---|
| 位置 | 身体位置 | 副驾/主驾/前排/后排 | 脚部/腰部/头部/肩部 |
| 操作 | `__act__` | 打开/关闭/调节/播放 | request/confirm/querymore（**对话行为**） |
| 对象功能 | 功能 | 通风/按摩/加热/蓝牙 | 驻车/智慧巡航/车道辅助（**ADAS**） |
| 调节内容 | `__tgt__` | 模式/温度/方向/风量 | 天气/气象/路况/剩余时间 |

**影响**：`REPORT.md` 早前版本把 `对象功能` 写成 `功能`，是错的，已修正。

## S4 槽位值归一化

### D4.1 规范形用**中文**，取簇内最高频原形

**决策**：`主驾/主驾驶/主驾的/驾驶位/驾驶座 → 主驾`，而不是 `→ driver`。

**为什么**（三条，按重要性）：
1. **可核对性**：中文规范形能逐条对回 MAC-SLU 原始数据；英文表需要双重核对（合并对不对 + 翻译对不对）。
2. **规范形可机械选出**：簇内最高频的原形。英文则要求你在 `passenger` / `front_passenger` / `co_driver` 之间做不可核对的判断。
3. **领域语言**：报告可读性。

**实测 token 成本**（中文 vs 英文，Qwen3-0.6B tokenizer）：输出侧每条差 0–3 tok；
`副驾` = 2 tok，`passenger` = 2 tok；`主驾` = 2 tok，`driver` = 1 tok。
**在噪声里，不是决策因素。**

### D4.2 **不做轴拆分**

**决策**：`位置` 保留为单一字段，`左前` 保留为独立规范形（不并进 `主驾`，也不拆成 `side=左,row=一排`）。

**为什么**：本实验不是在做通用车型 schema。P1 和 P2 看到的是**同一个 enum**，
多几个值不偏袒任何一臂。判据是「**金标唯一**」，不是「语义正确」。

**硬约束只有两条**：映射必须是**函数**（一值一映射，由 `_value_map()` 的冲突检测强制），
规范形集合必须**可枚举**。

### D4.3 建表用**全量**数据，不用 train-only

**决策**：映射表由全部 train+dev+test 的标注词表构建。

**为什么**（三条）：
1. 映射表定义的是**输出空间**（工具的参数取值域），生产环境里是**给定的**，不是模型学出来的。用全量建表是定义任务，不是拟合测试集。
2. **P2 的知识只来自 train，跟表建在哪无关。** 表建在全量上，P2 依然会在 train 没见过的规范值上失败——失败模式不会消失，只是从「样本被丢弃」变成「样本被答错」。
3. **「答错」比「丢弃」有信息量。**

**唯一必须坚持的**：建表时喂给 LLM 的输入只能是「槽位取值 + 频次」，**不能喂 query 或答案**。
只喂词表，表就是**标注词表的函数**，跟数据划分无关。

### D4.4 映射表用「规范形 + 变体列表」紧凑格式

**决策**：`rules/value_clusters.tsv` 一行一个规范形，变体用 `|` 分隔。
未出现在表中的原值 → 保持自身（identity）。

**为什么**：平铺形式是 2301 行；紧凑形式约 200 行，可读、可 review。
展开成扁平映射由 `common.Rules._value_map()` 在加载时完成，扁平形式不落盘（避免双份真相）。

### D4.5 `value` 做**轻度**归一化

**决策**：只合并明确的大小/方向/相对量标记（`调高/大一点/调大 → 调高`），
数值与枚举保持原形。

**为什么**：`value` 是**多态槽位**——它的类型依赖 `调节内容`（温度→数值、风向→枚举、风量→档位）。
逐值映射是错的。**这是全数据集中归一化程度最低的槽位，报告里已明说。**
实测：632 → 529 个取值（降 16.3%），top-1 集中度 0.029 → 0.081。

### D4.6 S4.5 长尾值过滤，**只对会写进 enum 的槽位生效**

**决策**：`config.json: min_enum_count = 2`。
取值种数 ≤ `max_enum_size`(30) 的槽位，enum 只保留 train 中出现 ≥2 次的规范值；
**使用更稀有值的样本丢弃**。半开放/自由文本槽位不受影响。

**为什么**：enum 槽位里混着标注噪声——`可以关了`、`弄回去`、`座`、`抬` 都成了 `veh.座椅` 的 `操作` 候选值。
这些对 P1/P2 都是纯噪声，且会把 schema 撑爆。

**为什么只对 enum 槽位生效**：第一版对**所有**槽位生效，结果 train 8219 → 3586（丢 56%），
因为 `value`（632 个取值）几乎每个样本都含稀有值。半开放槽位本来就声明为 `string`、不要求唯一，不该过滤。

**阈值选择**：`min_enum_count = 2` vs `3` 实测对比 —— 3 时 train 6723 / eval 977，2 时 train 7165 / eval 1027。
取 2，保住 5% 的 eval 样本。

## S5 金标构造

### D5.1 缺省参数直接省略（不写 `null`）

**决策**：`{"tool": ..., "arguments": {存在的参数}}`。

**为什么**：实测**样本内重复槽位名 0%**，不存在多值参数；缺省即无。写 `null` 只会增加输出 token。

### D5.2 schema 参数收录条件：≥2% 且 ≥5 次

> ⚠️ **已被 D5.5 取代（2026-10-21）**。本条记录的是当时的决策与理由，保留以备对照。

**决策**：`config.json: schema_param_min_ratio = 0.02, schema_param_min_count = 5`。

**为什么**：第一版用「参数须覆盖 95% 的样本」，结果**参数中位数 = 1**（太严，只有 `操作` 达标）。
正确的问题不是「这个参数出现在多少比例的样本里」，而是「这个参数是不是该工具的常规接口」。

### D5.3 `max_enum_size = 30`

**决策**：取值种数 > 30 的槽位，schema 里只声明 `{"type": "string"}`，不列 enum。

**为什么**：`歌曲名`（956 个取值）这类自由文本列 enum 没有意义，且会把 schema 撑爆。

### D5.4 描述生成：`rules/descriptions.tsv`，示例 query 只用 train

**问题**：第一版 schema 里参数的 `description` **完全缺失**，工具级描述也只是占位符 `f"{t} 车载指令工具"`。
这是 pipeline 设计时的遗漏——而 description 是 schema 的一部分，**P1 在 prompt 里能看到、P2 看不到**，
所以它是 P1/P2 差异的组成部分，必须显式构造。

**决策**：新增 S5.1。产物同样是可 review 的表 `rules/descriptions.tsv`，格式 `tool / slot / description`：

```
slot = *        → 该工具的描述
tool = *        → 该槽位的全局默认描述
(tool, slot)    → 该工具下的覆盖（优先级最高）
```

解析优先级：`(tool, slot)` > `(*, slot)` > 槽位名兜底。实测 **41/41 工具、216/216 参数全覆盖**。

**写法约定**：描述说清「这个参数是什么」，**不重复枚举取值**（`enum` 已承载取值）。
（第一版 `操作` 写成了「操作类型：播放、调节、打开、关闭、查找、设置、移动等」，
对 `veh.座椅` 来说 `播放`/`查找` 是误导，已改为「对该工具执行的操作类型」。）

**证据来源分两类**，`src/clean/dump_descriptions.py` 导出：

| 证据 | 来源 |
|---|---|
| 槽位名、取值、频次 | 全量 |
| 示例 query | **只用 train split** |

**为什么示例 query 只用 train**：`description` 属于 schema，是 P1 推理时**给定的任务定义**。
用 train 语料写描述，等同于在训练集上做 prompt engineering，是标准做法；
**用 eval 语料写则会携带评测集信息，构成泄漏**。这与 D4.3「建表只喂词表、不喂 query」是同一条原则的延伸。

**代价（实测）**：description 自身占 **2256 tok**，是 schema 块的 **46%**。

| | tokens |
|---|---:|
| P1 `<tools>` 块（含 description） | 7172 |
| 同上去掉 description | 4916 |
| description 净开销 | 2256（+45.9%） |

**顺带得到一个免费消融臂**：删掉全部 description，schema 立刻省 31%。
若「P2（无 schema）≈ P1（schema 去掉描述）」，说明模型并不需要这些描述——那本身就是结论。
**本实验暂不做这一臂，记录在此。**

### D5.5 参数契约：每工具 1–4 个参数，schema 与金标必须同口径（2026-10-21）

**问题**：D5.2 的「≥2% 且 ≥5 次」收的是**该工具可能出现的参数并集**，
而金标是**该样本实际标注的参数**。两者口径不同，于是模型照着 schema 补全，反被判错。

实测形状：

| 观测 | 数值 |
|---|---:|
| schema 参数在样本中的中位覆盖率 | **7%** |
| 金标参数不在 schema 里的样本 | 687（7.2%） |
| 典型例：`播放收藏` schema 5 个参数 vs 47/119 条金标只有 `操作` | — |

这不是模型能力问题。本实验问的是「一个**相对简单**的工具能否被后训练训进权重」，
不是「模型能否猜出标注员的省略习惯」。

**决策**：新增 S5.2，用人工 review 的 `rules/tool_params.tsv` 作**参数契约**：

| 规则 | 含义 |
|---|---|
| `role = required` | 每条样本必须有；缺失时补 `fill`，补不了**丢样本** |
| `role = optional` | 金标有就评，没有不评 |
| 不在表里 | **cut**：schema 和金标同时删 |

判定方法（只看 train）：

- `required`：覆盖率 ≥95%；或该工具覆盖率最高的参数且 ≥75%
- `optional`：其余覆盖率 ≥30%，每工具最多 2 个
- `fill`：**只允许由工具名唯一确定的常量**（`播放音乐.操作=播放`、`提供地址.操作=查找` 两处）。
  内容型参数一律不补 —— 那是编造标注。

**效果**（`build.py` 实测）：

| | 旧 | 新 |
|---|---:|---:|
| schema 参数 | 216 | **94** |
| 每工具 中位 / 最大 | 5 / 12 | **2 / 4** |
| 金标平均参数 | 2.38 | **1.73** |
| dev + test | 1272 | **1235** |
| P1 prompt | 7133 tok | **5563 tok** |
| 4B P1 Tool Acc | 69.65% | **70.93%** |
| 4B P1 Call（严） | 17.37% | **22.27%** |
| 4B P1 Call（主，宽松） | 23.51%† | **45.67%** |

† 旧宽松口径只评枚举参数，不完全等价。

**同时改了主指标口径**（见 REPORT §2.5）：Call Acc 主指标 = `gold ⊆ pred`，模型多写的参数不扣分；
严口径（集合相等）作为次要指标并列报。理由：金标是稀疏标注，判「多写」为错会把标注问题记成模型问题。

**已知代价**：

- `查询路况`、`查询路程` 在契约里没留下参数（历史标注太稀疏），eval 共 12 条（1.0%）退化成纯工具选择。
- 被 cut 的参数不再参与评测 —— 本实验不测复杂参数填充。
- 契约是**人**定的表，不是阈值脚本产物；改表即改实验，必须记录在案（本文件就是记录）。

**被否决的做法**：

- **按众数自动补全内容参数**（`查询气象.气象 → 雨`、`导航.终点名称 → 世界之窗`）——
  实测会批量制造假金标，全部撤销，只保留两个操作类常量。
- **保留全部参数、只改指标**——治标。参数多、金标稀疏的根因还在，模型仍会被鼓励乱补。

## S6 分层标记

### D6.1 按「(工具, 槽位, 规范值) 三元组是否在 train 出现过」打标

**决策**：每个 eval 样本标 `seen` / `unseen_slots`。

**为什么**：这样 **train-only 建表的结果就是 `seen` 子集**——一次运行拿到两个数，
报告里可以分层报「主问题（能不能记住）」和「真实局限（记不住的边界）」。

## 验收结果与未达标项

| 指标 | 目标 | 实测 | 状态 |
|---|---|---|---|
| 映射表覆盖率（可建表槽位，eval） | ≥85% | **86.8%** | ✅ |
| 归一化后取值种数（操作） | 显著下降 | 433 → 136（**−68.6%**） | ✅ |
| top-1 集中度（操作） | 显著上升 | 0.128 → **0.344** | ✅ |
| 确定性 | 逐字节可复现 | ✅ 两次运行 sha256 一致 | ✅ |

### ⚠️ 未达标 / 已知局限

1. **覆盖率 86.8%，低于最初预注册的 95%**。
   残余缺口是 25+ 个槽位上频次 ≤5 的长尾值（最大单槽 `value` 92 例，其次 `模式` 42 例）。
   **强行合并这些会造成错误映射**（它们是语义上不同的值，只是恰好罕见），故按现状记录。
   影响：约 13% 的 eval 可建表槽位实例，其金标是「自身的原形」，模型基本不可能命中——
   但这对 P1/P2 是对称的，不偏袒任何一臂。

2. **`value` 槽位归一化程度低**（632 → 529，仅降 16.3%）。
   它是多态槽位，按 `调节内容` 分支处理需要约 100 条规则，本轮未做。报告已声明。

3. **eval 从 1272 降到 1027**（S4.5 丢弃 19%）。
   代价换来的是一份没有 `可以关了` 这类噪声的 enum。**这个取舍记在这里，供复查。**

4. **多意图样本（train 14.9%）本版整体丢弃**，未支持一次输出多个 tool call。
   已复核为可行的后续方向（可回收 train +23% / eval +28%），做法见 `REPORT.md` 附录 C — T1。

## 推理层决策（2026-10-20 首轮 M1 实测后新增）

完整结果见 `REPORT.md` 与 `results/`。这里只记决策。

### D7.1 工具名去掉 `it.` / `veh.` 前缀（可开关）

**决策**：`config.json: strip_tool_prefix`。默认 `false`，但**实验采用 `true`**。

**为什么**：首轮 M1 实测发现，0.6B 在 P1（schema 明明白白给出全名）下仍**系统性丢掉前缀**：

| | 条数 | 占比 |
|---|---:|---:|
| tool 名完全正确 | 68 | 11.2% |
| 只差 `it.`/`veh.` 前缀 | 219 | 36.0% |
| 完全不对（其中 102 条也是「去前缀的合法名」或「把 `操作` 值当工具名」） | 212 | 34.8% |
| 没输出 tool_call | 110 | 18.1% |

**前缀是本实验引入的命名约定，不是 MAC-SLU 自带的**（数据里只有 `车身控制` + `对象`，前缀是我用来区分 `it.`/`veh.` 两域的）。
它造成约 **46%** 的系统性损失，而这个损失与实验要问的问题（schema 在不在上下文里）无关。

**安全性**：41 个保留工具去前缀后**无碰撞**（已逐条验证）。

**效果**：P1 的 Tool Acc 从 **11.08% → 49.53%**，Call Acc 从 1.49% → 8.57%。

**实现**：`common.split_tool()` 末尾按开关截断；`Rules._descriptions()` 的键统一按去前缀形式存，
所以 `descriptions.tsv` 不需要维护两份。

### D7.2 system message 加「必须调用工具」指令

**决策**：在 P1 和 P2 的 system message 末尾**对称地**加一句
「你必须调用工具来完成用户的请求，不要用自然语言直接回答。」

**为什么**：Qwen3 模板原文是 "You may call one or more functions to assist with the user query." ——
"may" 对 0.6B 太弱，实测 **18.1% 的样本改用自然语言回答**（"请提供您的电话号码以便我为您拨打电话。"）。

**为什么对称**：P1 和 P2 必须只差 `<tools>` 块。指令加在两边，不破坏这个约束。

**效果**：格式合法率 90.09% → **95.05%**，Call Acc 8.57% → 9.20%。

### D7.3 `max_num_seqs = 256`（P1 已饱和）

**实测**（0.6B，每种范式 128 条）：

| max_num_seqs | 16 | 32 | 64 | 128 | 256 |
|---|---:|---:|---:|---:|---:|
| P1 条/s | 32.6 | 33.1 | 34.9 | 41.1 | **42.5** |

P1 在 256 处饱和 —— 它是 **prefill 受限**（每条 prompt 9425 tok 的 schema），不是 batch 受限。
P2 快一个数量级（500+ 条/s，prompt 只有 66 tok）。全量 1272 条：P1 约 30 秒，P2 约 1 秒。

> S5.2（D5.5）之后 schema 块降到 **5563 tok**、评测集 1235 条，复跑实测 P1 仍是 prefill 受限
> （22–23 条/s、约 700 tok/s 输出），256 的结论不变。

### D7.4 环境：ninja 必须在 PATH 上；max_model_len ≥ 10240

- vLLM 的 flashinfer 后端 JIT 编译采样算子时要 subprocess 调 `ninja`。
  它装在 venv 的 bin 下、**不在默认 PATH 里** → `src/infer.py` 显式加进去。
- **P1 的 prompt 是 9528 tok**（其中 schema 9425；S5.2 之后降到约 5700），vLLM 默认 `max_model_len=4096` 装不下。
  注意：**9425 而不是 REPORT 早前写的 7172** —— 7172 是用紧凑 JSON 手工渲染的，
  而 Qwen3 模板的 `tojson` 产生带空格的 JSON，多出 2331 tok 的格式开销。

### D7.5 greedy 不等于可复现：vLLM 有 ±0.5 pt 的跑间噪声（2026-10-21）

**实测**：同一模型、同一 prompt、`do_sample=False`，连跑两次，dev P1 有 **27/588（4.6%）** 输出不同。
原因不是采样，而是 vLLM 的 paged-attention / batch 调度在 bf16 下产生不同的归约顺序，
logits 在接近平局时 argmax 翻转。

**决策**：

1. 报告里**不再写**「greedy ⇒ 确定」。
2. 任何跨配置比较，**差异 < 1 pt 不解释**（噪声地板 ±0.5 pt）。
3. 需要精确比较时（例如 M1 vs M2），跑 3 次取中位数，而不是只跑 1 次。
4. 预测文件名**必须带模型后缀**（`--suffix _4b` / `_06b`）——
   第一次复跑时 0.6B 把 4B 的 preds 覆盖了，这个坑已经踩过。

证据：`out/preds/dev_P1_d_dt{1,2}.jsonl`。

## 训练层决策（2026-10-21）

### D8.1 训练数据只有 P2 —— P1 不参与训练

**决策**：M2 只在 `out/prompts/train_P2_d.jsonl`（7993 条，输入无 schema）上训练。

**为什么**：P1/P2 是同一批样本的两种渲染。若把 P1 也拿来训，模型学的是「读上下文里的工具清单」——
那正是本实验要作为**基线**的能力，会让「工具是否进了权重」这个问题失效。
P1 只在评测时用，测的是遗忘（M2/P1）。

**备选（暂不做，只在 M2/P1 崩了时考虑）**：P2 90% + P1 10% 混训。
一旦混训，M2 的定义就变了，必须作为独立臂报告。

### D8.2 三个训练臂：0.6B 全参 / 0.6B LoRA / 4B LoRA

| 臂 | 模型 | 方式 | 作用 |
|---|---|---|---|
| E1 | Qwen3-0.6B | 全参 | 最干净的「能否学进去」，排除 LoRA 容量干扰 |
| E2 | Qwen3-0.6B | LoRA r=16 | 与 E1 对比：LoRA 够不够 |
| E3 | Qwen3-4B | LoRA r=16 | 主力结果（4B 全参在 24 GB 上不可行） |

三臂**共用同一份数据、同一套超参（除 lr）、同一个评测链**，差别只在更新哪些参数。

### D8.3 超参：短序列 + 小数据，不需要大 max_len

| 项 | 值 | 依据 |
|---|---|---|
| max_len | 256 | 实测 mean 110.4、max 146 |
| batch × accum | 8 × 4 | bs=32 时 0.6B 全参 OOM（激活 + 151k 词表 logits） |
| epochs | 3 | 0.6B 全参 epoch3 loss 0.032，已接近记忆 |
| lr | 全参 2e-5 / LoRA 1e-4 | LoRA 需要高一个量级 |
| warmup | 3%（**按优化器步数**，不是微批） | 见 D8.5 |
| LoRA | r=16, alpha=32, dropout 0.05, 全线性层 | 工具名→参数名绑定需要 MLP |
| seed | 42 | 单 seed 先跑通，正式比较再补 3 seeds |

**实测成本**：0.6B 全参 9.2 GB / 70 s/epoch；0.6B LoRA 7.0 GB / 72 s/epoch；全程 7993 条 × 0.88 M tok。

### D8.4 LoRA 每轮存盘要 merge→save→unmerge，不能 merge_and_unload

**踩过的坑**：`merge_and_unload()` 就地销毁 LoRA 层，第一轮存完盘，第二轮就没有可训练参数了
（E2 第一次跑只出了 epoch1）。改成 `merge_adapter()` → 存 `base_model.model` → `unmerge_adapter()`。

**为什么必须 merge 后存**：M1 和 M2 要跑完全相同的推理路径。若 M2 走 adapter 加载、M1 走底座加载，
加载方式本身的差异会混进实验结论。

**第二个坑**：`merge_adapter()` 之后 `save_pretrained` 写出的键名仍是 `X.base_layer.weight`
（LoRA 包装层没被剥掉），vLLM 报 `no module named 'layers.0.mlp.down_proj.base_layer'`。
数值本身是合对的（实测 Δ 与 `B@A×α/r` 余弦 0.96–0.99，差异是 bf16 舍入），
所以只需重写键名：`src/merge_lora.py` 把 `X.base_layer.weight` → `X.weight`、删掉 `lora_A/B`。
`train.py` 存盘后会自动调用它。

### D8.5 lr schedule 按优化器步数推进

第一版按微批推进，grad_accum=4 时 warmup 提前 4 倍结束、余弦退火跑出定义域。
现在单独计数 `opt_step`，并对进度做 `min(1.0, ...)` 截断。

### D8.6 三臂结果：LoRA 在小模型上反而优于全参

| 臂 | M2/P2 Call | M2/P1 Call |
|---|---:|---:|
| 0.6B 全参 | 75.06% | 43.64% |
| 0.6B LoRA | **78.46%** | 49.15% |
| 4B LoRA | **82.35%** | 60.40% |

**发现**：0.6B 上 LoRA 比全参高 3.4 pt。7993 条数据训全参小模型会过拟合，
LoRA 的冻结底座是隐式正则。**以后小模型的对照实验优先用 LoRA**，全参只在需要「最大容量」时用。

**另一条**：M2/P1（60.40%）高于 M1/P1（45.67%），遗忘门槛不仅通过，还是正迁移。
训练时从未见过 schema-in-prompt，但学到工具词表后再给 schema，模型更会用。

## 控制实验决策（2026-10-21）

### D9.1 补 M2′：用 P1 渲染训练，把「训练」与「清单位置」两个因素分开

**问题**：M2/P2（82.35%）与 M1/P1（45.67%）同时差了两件事，不能直接归因于参数化。

**决策**：加训练臂 M2′——同样的 7993 条样本，只把训练输入的渲染换成 P1（schema 在 prompt 里）。
与 M2 的 epoch1 对齐比较（P1 训练 45–60 min/epoch，先做 1 epoch）。

**结果（0.6B LoRA，dev+test，epoch3，n=1235）**：

| 训练 | 评 P1 | 评 P2 |
|---|---:|---:|
| **P1**（M2′） | **78.46%** | **0.00%** |
| **P2**（M2） | 49.15% | **78.46%** |

**两个结论**：

1. **质量打平**：对角两格都是 78.46%，严口径 / Tool / ArgF1 差 0.7–1.2 pt，
   小于训练跑间方差（同配置重跑两次差 2.2 pt）→ 只能判「等价」。
   **参数化的收益不在质量，在成本**：推理 5563 tok/请求、训练每 epoch 便宜 ~45 倍。
2. **迁移不对称**：无清单训练能迁移到有清单（49.15%），反过来是 **0.00%**。
   拿掉清单就归零，格式仍 97.8% 合法 → 是词表崩，不是格式崩。
   清单在上下文里时，模型学的是「照抄」，知识不在权重里。

**这条控制实验推翻了先前那个「+36.7 pt」的读法** —— 它混淆了「训练」与「清单位置」。

**代价**：P1 训练每条 prompt 5673 tok（vs 110），单 epoch 贵约 45 倍——
上下文方案的训练成本本身就该计入成本表。

### D9.2 长序列训练的 `logits_to_keep`

P1 训练 OOM 的根因不是激活，是**词表 logits**：batch 1 × 5673 tok × 151936 vocab ≈ 3.4 GB（fp32 CE），
再加 backward 保存的副本。解法是只对最后 `target_len + 1` 个位置算 logits，
`labels` 同步切片（多留 1 位是因为第一个 target token 由前一位预测）。0.6B 峰值 15.6 GB。

## 成本实验决策（2026-10-22）

### D10.1 用「max_tokens=1 的端到端耗时」作 TTFT 代理

vLLM 离线 `LLM.generate` 不直接暴露 TTFT。用 `max_tokens=1` 测单请求端到端耗时，
它 = prefill + 1 个 decode step；decode 步在 P1/P2 上相同，所以**差值**可归因于 prefill。
另用 32-token 版本观察 decode 侧差异。

一次只跑一种 APC 设置（`enable_prefix_caching` 是引擎构造参数，切换必须重建引擎，
vLLM 不会把显存完全还回来），外层跑两个进程。

### D10.2 只报 req/s 会得出错误结论（2026-10-22 修正）

第一版成本测量用 `max_tokens=1` 报 req/s，得出「开缓存后吞吐差 9×」。这个数字有两个问题：

1. **输出长度不固定**：不同请求生成的 token 数不同，req/s 不可比。改用 `ignore_eos=True` + 32 token。
2. **req/s 混淆了「请求更便宜」和「引擎更快」**：P1 每条请求 5647 输入 token，P2 只有 84。

修正后（`src/throughput.py`，扫并发 1/8/32/100）：

- 并发 1：P1 只慢 1.10×（379.7 vs 343.7 ms）——单用户场景缓存基本补平。
- 并发 100：输出 tok/s 差 4.4×（1300.5 vs 5764.2）——decode 侧的 KV 读取补不掉。
- 不开缓存：差 47×，且 P1 饱和在 ~73 tok/s。

**结论不变，但量级更准**：前缀缓存补 prefill，不补 decode 与 KV。

### D10.3 结果：前缀缓存只补 prefill，不补 decode 与 KV

| 4B（固定输出 32 token） | P1 | P2 | 倍率 |
|---|---:|---:|---:|
| TTFT 冷启（c=1） | 359.6 ms | 13.3 ms | 27× |
| TTFT + APC（c=1） | 23.4 ms | 12.1 ms | 1.9× |
| 单请求 32 token + APC（c=1） | 379.7 ms | 343.7 ms | 1.10× |
| 输出 tok/s + APC（c=100） | 1300.5 | 5764.2 | 4.4× |
| 输出 tok/s 无 APC（c=100） | 73.4 | 3463.4 | 47× |
| KV | 0.485 GiB | 0.007 GiB | 67× |

**决策含义**：报告里不能再写「schema 的 prefill 可被前缀缓存吃掉，所以成本优势归零」。
正确的表述是三项分开：TTFT（可补）、吞吐（不可补）、KV（不可补）。
这也把论文的论点从「参数化省推理算力」改成更准确的一句：
**参数化省的是 decode 时的 KV 读取与显存，不只是 prefill。**
